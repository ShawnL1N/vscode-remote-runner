# VS Code Remote Runner

<p align="right">
  <a href="./README.md">English</a> ·
  <strong>简体中文</strong>
</p>

`vscode-remote-runner` 允许本地 Codex 在用户明确请求后，将命令输入到一个已经完成身份验证的 VS Code Remote SSH 终端中。它不会自行建立 SSH 连接，也不会获取服务器密码或私钥。

当前版本支持两种模式：

- **单次执行（默认）：** 输入一条命令，默认按下 Enter，然后立即退出。
- **托管监控（仅在明确启用时）：** 启动后台任务、创建托管结果文件，并持续轮询，直到任务完成或失败。

## 为什么选择它，而不是让 Codex 直接 SSH？

与向 Codex 提供独立的直接 SSH 连接相比，这个 Skill 提供了一条权限更窄、由用户控制程度更高的通道：

- **无需向 Codex 交付单独的服务器凭据。** Skill 复用用户已经完成身份验证的 VS Code Remote SSH 会话，不需要向 Codex 提供密码、私钥、SSH Agent 或独立登录配置。
- **Codex 无法在之后自行重新连接。** 关闭 VS Code SSH 会话就会切断这条通道；Skill 不会保留可复用的服务器入口。
- **保留已有的访问控制。** 连接可以继续使用用户批准的 VS Code 配置、跳板机、MFA 流程或其他组织特定的登录方式，无需在 Codex 中重新实现这些身份验证流程。
- **命令始终可见且可中断。** 提交的命令会显示在所选终端中，用户可以使用熟悉的 VS Code 操作检查、停止或接管会话。
- **默认权限有意保持在较小范围。** 单次执行模式只会把用户明确要求的命令输入当前选中的终端。它不会创建新终端、选择其他服务器，也不会自行获得不受限制的远程 Shell 访问权。
- **连接配置更少。** 无需另外配置 Codex SSH 客户端、把密钥复制进 Codex 环境、暴露新的远程入口或在服务器端安装 Agent。
- **可以绕过本地沙箱或网络连接限制。** 当 Codex 无法自行建立 SSH 连接、但 VS Code Remote SSH 已经连接时，Codex 仍可通过现有桌面会话提交用户要求的终端命令。
- **适用于不同的 Remote SSH 服务器。** 窗口检测不会硬编码用户名、主机名、IP 地址、项目路径或特定服务器。

它不能普遍替代直接 SSH。对于无人值守自动化、交互式 Shell、大文件传输和高频命令执行，直接 SSH 更可靠。此 Skill 更适合重视凭据隔离、用户明确控制和复用现有 VS Code 会话，而不是追求最大自动化可靠性的场景。

## 1. 工作原理

```text
用户明确调用 Skill
        ↓
Codex 构造一条单行命令并判断其风险
        ↓
本地 PowerShell 脚本寻找 VS Code Remote SSH 窗口
        ↓
Windows UI Automation 定位现有终端的输入控件
        ↓
脚本粘贴命令，在适当情况下提交，
然后恢复原始剪贴板内容
        ↓
命令在已经完成身份验证的远程 Shell 中运行
```

该 Skill 复用用户已经建立的 VS Code Remote SSH 会话。Codex 不在服务器上运行，服务器也不需要访问 OpenAI。只有当提交的命令本身需要下载代码、依赖、模型或其他外部资源时，服务器才需要访问外部网络。

## 2. 适用场景

以下情况适合使用该 Skill：

- 本地 Codex 可以正常工作，但服务器不方便访问 OpenAI。
- 用户已经通过 VS Code Remote SSH 连接到服务器。
- Codex 无法或不应获得单独的 SSH 私钥和不受限制的远程访问权。
- 用户希望 Codex 输入 `nvidia-smi`、启动脚本或开始训练等命令。
- 服务器文件已经挂载到本地，因此 Codex 可以通过挂载目录监控日志和结果。
- 用户明确要求 Codex 持续监控长时间运行的命令，直到成功或失败。

以下情况不应使用该 Skill：

- Codex 需要登录、输入密码、完成 MFA 或处理安全提示。
- VS Code Remote SSH 尚未连接。
- 任务需要交互式编辑器、REPL、全屏应用或多轮终端对话。
- 无人值守期间桌面会被锁定，或 VS Code 无法保持可用。
- 任务需要不受限制的服务器文件传输、任意目录访问或稳定的远程 API。此时应使用受控的 SSH、SFTP 或 MCP 集成。

## 3. 环境要求

### 单次执行

- Windows 10 或 Windows 11。
- 未锁定的桌面会话。
- 已经通过 Remote SSH 连接的标准 Visual Studio Code 窗口。
- 窗口标题同时包含 `[SSH: ...]` 和 `Visual Studio Code`。
- 一个可见、已选中、处于空闲状态且输入行为空的集成终端。
- 如果终端被拆分为多个窗格，目标窗格必须已经获得键盘焦点。如果多个窗格可见但无法唯一确定焦点，Skill 会安全停止，而不是选择找到的第一个窗格。
- 本地可以使用 Windows PowerShell、Windows UI Automation 和剪贴板。

### 内置托管监控

托管监控还要求：

- 类 Linux 的远程 Shell。
- 远程系统中包含 `bash`、`base64` 和 `nohup`。
- VS Code 终端 Shell Integration 正常工作。
- 监控期间，选中的终端保持由 Codex 独占。
- VS Code 内置命令 `Terminal: Copy Last Command Output`。如果 VS Code 使用本地化界面，可能需要改用对应的本地化命令名称。

## 4. 安装

请保持解压后的目录结构不变：

```text
vscode-remote-runner/
├── SKILL.md
├── agents/
│   └── openai.yaml
└── scripts/
    ├── vscode_remote_terminal.ps1
    └── vscode_remote_monitor.ps1
```

将整个 `vscode-remote-runner` 目录放入 Codex 可以识别的个人 Skill 目录。当前包已验证的 Windows 路径是：

```text
%USERPROFILE%\.codex\skills\vscode-remote-runner\
```

如果其他 Codex 安装从 `%USERPROFILE%\.agents\skills\` 发现个人 Skill，请把同一个目录放在那里。如果 Skill 没有自动出现，请重启 Codex。

## 5. 模式选择

| 用户意图 | 模式 | 结果文件 | 自动按 Enter |
|---|---|---:|---:|
| 查看 GPU、工作目录或 Git 状态 | 单次执行 | 否 | 是 |
| 启动普通脚本或训练，但不持续监督 | 单次执行 | 否 | 是 |
| 明确要求“持续监控”“看到结束为止”或同等含义 | 托管监控 | 是 | 是 |
| 删除、覆盖、终止、修改环境或传输秘密 | 先审查 | 视任务而定 | 否；仅在第二次确认后提交 |

运行时间长本身不会自动启用监控。只有用户最新的请求明确要求持续监督时，才允许使用托管监控。

## 6. 单次执行流程

1. 通过 VS Code Remote SSH 连接服务器。
2. 打开一个已有的集成终端，并等待远程命令提示符出现。
3. 确认终端空闲且输入行为空。
4. 明确调用该 Skill，例如：

   ```text
   $vscode-remote-runner 查看服务器当前的 GPU 使用情况。
   ```

5. Skill 搜索可见的 VS Code Remote SSH 窗口。
6. 如果恰好有一个候选窗口，Skill 会自动选择；如果存在多个候选窗口，它会安全停止并要求指定目标。
7. 脚本聚焦已有终端、粘贴命令，并默认按下 Enter。
8. 脚本恢复原始 Windows 剪贴板并退出。
9. 用户直接在终端中查看即时输出。

对于 `nvidia-smi`、`pwd`、`ls` 和 `git status` 等短检查命令，Skill 不会创建运行目录、日志、PID 文件、状态文件或结构化结果。

本地脚本返回的 JSON 回执只能证明输入已经送达，不能证明远程命令已经成功完成。

## 7. 高风险命令的先审查流程

以下操作必须先以“只粘贴、不提交”的方式供用户审查：

- 删除文件、目录、环境、分支或记录。
- 覆盖、截断、强制替换、重置或不可逆地迁移数据。
- 终止进程、训练任务、服务、容器或会话。
- 安装、删除或升级软件包，或修改系统设置、环境、权限或所有权。
- 在命令中输入密码、令牌、私钥或其他秘密。

流程如下：

1. Codex 显示完整命令并指出其风险类别。
2. Skill 粘贴命令，但不按 Enter。
3. 用户在终端中检查实际命令。
4. 用户发送一条新消息，确认命令未被修改且可以提交。
5. Skill 只发送 Enter，不会再次粘贴命令。

如果用户已经编辑或提交该行，或者终端状态不确定，Skill 必须停止。它不得盲目提交，也不得把命令运行两次。

## 8. 长时间任务：推荐的监控架构

如果服务器目录已经挂载到本地，优先使用相互分离的架构：

```text
执行通道：vscode-remote-runner → 已认证的远程终端
结果通道：服务器日志和 JSON → 本地挂载目录
监控通道：Codex 定时任务 → 周期性只读检查
干预权限：由用户保留
```

完整流程：

1. 训练控制器把日志、状态、指标和最终结果写入服务器项目目录。
2. 通过映射盘或其他本地只读可见的挂载方式暴露该目录。
3. 使用 `vscode-remote-runner` 启动训练命令。
4. 创建一个 Codex 定时监控任务，例如每五分钟检查：
   - 控制器状态和最后更新时间。
   - 当前阶段、种子、epoch 和最终 epoch。
   - `history.json` 是否持续推进。
   - 日志中的 `traceback`、`CUDA OOM` 和 `failed` 标记。
   - 阶段验证输出和最终汇总。
5. 只报告阶段切换、新种子、连续无进展、错误和完成。
6. 不允许监控任务启动、重启、终止或修改任何进程或文件。
7. 完成后审核最终指标并停止监控任务。

监控任务必须区分：

- 挂载目录已断开、无法访问或内容陈旧。
- 训练进程确实已经停止推进。

条件允许时优先使用这种架构。它不需要向 Codex 提供 SSH 私钥，也不需要保留训练终端用于轮询。

## 9. 长时间任务：内置托管监控

只有在用户明确要求持续监控，并且没有更好的挂载目录监控方式时，才使用内置模式。

请求示例：

```text
$vscode-remote-runner 启动这条训练命令，并持续监控到完成或失败。
```

托管监控会：

1. 捕获命令以及终端当前的远程工作目录。
2. 在以下位置创建私有运行目录：

   ```text
   ~/.codex-runs/<run_id>/
   ```

3. 使用 `nohup` 启动后台运行器。
4. 将标准输出和标准错误写入 `run.log`。
5. 只针对该 `run_id` 周期性提交轮询命令。
6. 使用 VS Code 内置的 Copy Last Command Output 功能传输托管结果文件内容，而不使用截图或可视终端解释。
7. 为每次轮询分配新的 probe ID，只有当 run ID、probe ID 和两个协议哨兵全部匹配时，才接受复制的输出。
8. 每次轮询只调用一次 Copy Last Command Output；如果 UI 传输状态不确定，则安全停止而不是重试。
9. 默认仅返回最新一行日志，并限制在 2 KB；只有在明确诊断失败时才请求更长的日志尾部。
10. 当状态变为 `completed` 或 `failed`、用户要求停止、终端归属不确定或结果通道失败时停止轮询。

托管运行目录包含：

| 文件 | 用途 |
|---|---|
| `status` | `queued`、`running`、`completed` 或 `failed` |
| `pid` | 后台运行器 PID |
| `run.log` | 未经修改的标准输出和标准错误 |
| `exit_code` | 最终进程退出码 |
| `started_at` | UTC 开始时间 |
| `finished_at` | UTC 结束时间 |
| `work_dir` | 提交时的远程工作目录 |
| `command.b64` | Base64 编码的原始命令 |
| `runner.sh` | 私有后台运行脚本 |
| `result.json` | 由任务写入的可选结构化结果 |

此模式会暂时把所选终端保留为轮询通道。监控期间请勿手动使用同一个终端。

## 10. 安全边界

- Skill 只在用户明确调用后运行；隐式调用已禁用。
- 它不会创建或切换终端，也不会登录服务器。
- 它不会处理密码、MFA、安全提示或隐私提示。
- 它不会把截图、终端布局或回滚缓冲区视为执行证据。
- 当存在多个 SSH 窗口且未指定目标时，它会安全停止。
- 每次发送系统级按键前，它都会验证之前记录的精确 VS Code 窗口句柄仍是前台窗口；仅标题匹配并不足够。
- 在托管轮询期间，它还会在粘贴命令名称和按 Enter 前，确认同一个已启用的命令面板输入框仍然获得焦点。
- 默认只接受单行命令。
- 每次操作后都会恢复原始剪贴板。
- 高风险命令必须先只粘贴供用户审查，并在得到新的明确确认后才能提交。
- 输入状态不确定时绝不会盲目重试。
- 远程命令以当前远程账户的权限执行，不受本地文件系统沙箱保护。

## 11. 限制

- 当前实现仅支持 Windows 本地桌面。
- 它依赖标准 VS Code 窗口标题和 `xterm-helper-textarea` 终端控件，VS Code 更新可能改变这些实现细节。
- Cursor、VSCodium、浏览器版 VS Code 和其他编辑器尚未验证。
- 脚本无法判断终端是否真正空闲、输入行是否为空，或是否有交互式程序正在占用终端。
- 桌面锁定、终端隐藏、身份验证对话框或权限提示都会导致流程失败。
- 单次执行模式无法读取或验证终端中的可见输出。
- 托管监控依赖 VS Code Shell Integration 和内置复制命令，本地化界面可能需要不同的命令名称。
- 托管轮询会短暂打开 VS Code 命令面板，并且只能调用 Copy Last Command Output。
- 当远程环境缺少 `bash`、`base64` 或 `nohup` 时，无法使用托管监控。
- 挂载目录监控依赖挂载的可用性和缓存新鲜度。挂载断开不能被视为训练失败的证据。
- Skill 不会绕过服务器权限、SSH 策略、网络策略或本地 Codex 审批要求。

## 12. 故障排查

### 找不到 SSH 窗口

- 确认 VS Code 窗口可见并已通过 Remote SSH 连接。
- 确认标题同时包含 `[SSH: ...]` 和 `Visual Studio Code`。
- 确认使用的是标准 VS Code，而不是尚未支持的编辑器分支。

### 找到多个 SSH 窗口

- 明确指定目标窗口，或只保留需要操作的 SSH 窗口。
- 不要要求 Skill 根据最近活动情况进行猜测。

### 找不到终端输入控件

- 打开一个已有的集成终端并保持可见。
- 确认终端没有折叠、关闭或移出屏幕。
- Skill 不会替用户创建终端。

### 命令已提交，但结果未确认

- JSON 回执只能证明命令已被输入。
- 用户直接在终端中查看即时输出。
- 通过挂载文件或托管结果文件确认长时间运行的任务。
- 当执行状态不确定时，绝不要再次提交相同命令。

### 托管监控无法取得状态

- 确认 VS Code 终端 Shell Integration 正常工作。
- 确认 Copy Last Command Output 的名称与 VS Code 界面语言匹配。
- 确认被监控的终端没有用于其他命令。
- 如果无法验证哨兵，请停止托管监控，改用挂载目录监控。

### 挂载文件停止更新

- 首先确认映射盘或挂载仍可访问。
- 将文件修改时间与控制器心跳进行比较。
- 在报告停滞前要求连续多次无进展，避免把短暂缓存或网络延迟误判为训练失败。

## 13. 推荐操作规则

1. 即时检查命令直接运行，并由用户在终端中查看输出。
2. 普通启动命令只提交一次，不自动启用监控。
3. 存在本地挂载时，优先使用 Skill 启动任务，再使用定时只读监控。
4. 只有在用户明确要求持续监控且无法使用挂载目录时，才使用内置托管监控。
5. 对高风险命令始终采用“粘贴、用户审查、新确认、仅提交”的流程。
6. 不要向 Skill 提供主 SSH 密钥、服务器密码或长期有效令牌。
7. 监控只负责观察和报告。重启、终止或修改训练参数必须另行授权。
